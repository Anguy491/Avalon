# ADR-002：Node.js/Fastify 长运行服务，托管供应商延后决定

- 状态：已接受
- 日期：2026-08-13

## 背景

服务端要维护实时连接、执行短事务、广播个性化投影并运行房间过期任务。移动端和协议均使用 TypeScript；项目尚未确定云供应商、预算、区域和生产账号。

## 决策

- 运行时使用初始化时的 Node.js 活跃 LTS，并在仓库和容器中精确锁定；
- HTTP 框架使用 Fastify；输入与输出均绑定协议 Schema；
- 实时层使用与同一 HTTP 服务共享鉴权的 Socket.IO；
- 应用部署为可水平扩展的长运行容器，不以短生命周期函数承载实时连接；
- 生产为单区域、至少两个应用实例，使用托管 PostgreSQL、托管 Redis 和独立后台任务；
- 云供应商、区域与域名在 `M0-GATE-01` 由用户确认，后续新增供应商 ADR，不改变本 ADR 的运行时职责。

版本号不写死在本文。M0 必须在 `package.json`、锁文件、容器基础镜像和依赖更新策略中记录可复现版本。

## 结果

端到端 TypeScript 降低协议映射成本；Fastify 的 Schema 边界适合拒绝非法载荷；容器允许标准 WebSocket 生命周期和优雅排空。

代价是需要管理进程、数据库连接池、Redis adapter、滚动部署和后台任务，不能把这些职责交给纯静态托管。

## 未采用方案

- 在 Expo Router API routes 中承载权威服务器：移动 Web 与游戏服务部署耦合，实时扩展路径不明确；
- 纯 BaaS 客户端写数据库：无法自然保证命令权限、幂等与自动裁决事务；
- 立即绑定 Cloudflare Durable Objects 或特定 PaaS：在预算和数据区域未确认前会产生不必要锁定；
- NestJS：结构完整但 MVP 样板和抽象更多，Fastify + 显式模块边界已足够。

## 验证

- 服务能在本地容器和候选生产平台运行相同构建产物；
- 滚动重启时客户端通过完整投影恢复；
- 10,000 连接基线压测满足 `NFR-003`–`NFR-004`；
- 未知字段、超限载荷和错误 content type 在进入应用服务前被拒绝。
